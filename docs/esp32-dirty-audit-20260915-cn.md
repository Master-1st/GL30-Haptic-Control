# GL30：按帧跳过 framebuffer 比较与显示链路代码审计

任务开始日期：2026-09-15。项目：`G:\Agent\GL30-Haptic-Control`。

硬件：Waveshare ESP32-S3-Touch-AMOLED-1.32，466×466 RGB565、CO5300。环境：Windows、AgentDock 0.8.3、已安装 ESP-IDF 5.5.1。最终应用已通过 COM11 烧录；未访问 COM4、未烧录 STM32、未使能电机。

## 1. 最终结论

动画/明确模型变化帧已经不再执行 434,312 字节的整帧 `memcmp`。默认 OLED 提交仍会进行相同帧去重；未知原因的重绘、静态画面、失败恢复与唤醒恢复没有被简单地改为无条件连续送屏。

最终刷新截止间隔为 **28 ms**。三组各 60 秒连续菜单旋转测试，共完成 **6,429 帧 / 180.052476 s，35.706257 FPS**。实际帧间隔合并统计：P50 **28.001 ms**、P95 **28.499 ms**、P99 **28.983 ms**、最大 **37.737 ms**。

这不是“每一帧严格 28 ms”：6,426 个组内帧间隔中有 **4 个超过 35 ms，0 个超过 40 ms**。三组采样内没有光栅帧编号跳过，`compare_calls_delta=0`、每帧 `compare_us=0`，显示错误、输入队列丢弃和电机发送均为 0。该性能结论只覆盖连续菜单工作负载，不外推到所有应用页面、真实电机联调或长期运行。

证据入口：[aggregate.json](../outputs/esp32-dirty-audit-20260915/aggregate.json)、[三组原始结果](../outputs/esp32-dirty-audit-20260915/final-3x60s/summary.json)、[USB 功能结果](../outputs/esp32-dirty-audit-20260915/usb-smoke-final.json)。

## 3. 跳过比较的准确契约

新增接口：

```c
void OLED_MarkFrameChanged(void);
void OLED_Poll(void);
```

`OLED_MarkFrameChanged()` 标记的是 **当前物理绘制缓冲区对应的一帧**，不是一个永久全局开关。标记只说明这次重绘有明确变化意图、允许省略可选去重，不证明每个像素一定改变。标记在 Busy 时保留；Clear、Fill、初始化和缓冲区复用会重置。强制全帧恢复是另一个独立状态，优先级高于可选比较。

GL30 的 `known_dirty` 会跨输入采样保留到真正绘制。菜单动画、运行计时器/秒表、动态灯效及明确输入变化，在绘制完成后标记当前帧。无明确变化的外部 `KK_UI_Invalidate()` 默认仍比较。电源唤醒已恢复稳定帧，其随后可能相同的重绘不无条件标记，避免重复帧占用 DMA。

典型流程：

```text
按时间顺序消费输入与更新模型
    → 有 READY 帧且 DMA 空闲：先提交 READY
    → 没有 READY 帧且到绘制截止时间：绘制新帧
    → 明确变化时标记当前绘制缓冲区
    → UI 所有者消费绘图期间到达的真实完成事件
    → 检查晚到错误；成功且空闲才提交新帧
```

缓冲始终有界：最多一帧已冻结传输，加一帧绘制/等待提交。**等待中的 READY 不会为了追赶下一截止时间再次被覆盖绘制**；输入状态仍继续消费，随后新帧呈现最新状态。没有积压一串过时动画帧。

代码位置：`components/kk_oled/graphics/kk_oled.c`、`components/gl30_ui/src/gl30_demo.c`、`components/kk_ui/src/kk_ui.c`。上述路径相对 `firmware-esp32/`。

## 4. 审计实际发现与修复

### A. 已画好的帧被再次重绘覆盖

仅跳过比较并压到 28 ms 后，10 秒短测看似正常，但三组 60 秒分别出现最大 **59.401 / 59.513 / 60.129 ms** 的长间隔，并出现光栅编号跳过。先提交 READY、绘制后 poll 的中间方案仍有约 49 ms 长尾；最终再禁止在 READY 尚未交出时重画，三组最终 trace 的光栅编号跳过为 0，最大间隔为 37.737 ms。

失败证据保留在 `candidate-unpaced-3x60s/` 与 `candidate-poll-only-3x60s/`。这些是明确的中间失败版本，不作为当前固件性能。没有删掉长尾数据只展示最优短测。

### B. DMA 失败后，Busy/重新初始化保护不完整

旧 BSP 消费错误结果后可能解除 `s_frame_busy`；初始化函数还先判断 `s_initialized`，后判断失败。这使软件重新初始化可能清空仍有未确认 DMA 所有权的显存。

修复：失败先行检查；致命 DMA 故障将 Busy 保持为真；失败结果可以读取，但不解除内存隔离。晚到完成回调不自动恢复。任何部分初始化失败也锁存，不重复分配或重复初始化已被部分占用的外设。

**BSP 级致命故障的恢复方式为硬件复位/重新上电。** 这与主机可确定已终止的模拟 OLED 错误重发，是不同层级的恢复契约。

### C. SPI 出错后可能漏收正在进行的 copy completion

旧分支只有 `completed && copy_pending` 才等待搬运完成。现在即使 SPI 已失败，也尝试收取已经提交的 copy 完成；任何仍不确定的内存归属都保留到复位，禁止继续复用。

### D. 两块 framebuffer 没有分别缓存行隔离

旧声明只保证整个二维数组的首地址 64 字节对齐。434,312 不是 64 的整数倍，因此第二帧起点不是 64 字节边界，两帧边界会共享缓存行。

现在每帧物理存储跨度填充到 **434,368 字节**，每帧额外 56 字节、两帧共增加 112 字节。实际比较、绘制有效范围和送屏长度仍为 434,312，不会把 padding 送到 CO5300。

这项修复消除潜在缓存行共享，不宣称先前每一帧都发生了缓存错误。实际安装的 ESP-IDF 5.5.1 `async_memcpy_gdma.c` 已经执行源缓存 C2M 同步，未重复加一遍整帧 cache flush。

### E. 初始全黑帧可能被错误去重

内存中两帧初始化均为零，并不代表面板 GRAM 已经清黑。旧初始化可能把第一次黑帧当作相同帧跳过。现在初始化强制第一次完整提交，后续相同帧再正常去重。

### F. 统计口径和验收定义遗漏

上轮约 **0.5 ms 的 `copy_us` 只代表等待搬运完成的剩余时间**，没有包含 `esp_async_memcpy()` 内部的描述符、缓存同步及提交工作。不能将其解释为整个搬运相关工作只剩 0.5 ms，更不能以两个不同口径的数字证明“全部 copy 成本下降 95%”。

本轮新增 `metric_schema=2`，分别输出 `copy_submit_us`、`copy_wait_us`、`copy_span_us`。旧 `copy_us` 暂保留为 `copy_wait_us` 的兼容别名。`copy_span_us` 为各段 API 入口至回调跨度之和，包含重叠时间，不是纯 DMA 总线占用测量。最终每帧提交调用加剩余等待 P95 为 **3.397 ms**；物理 PSRAM→SRAM 搬运依然存在。

同时修正：独立的帧编号只能证明不同的提交/光栅任务，不能证明像素内容一定不同。benchmark 字段改为 `completed_raster_frames` 并明确 `pixel_uniqueness_verified=false`，不把跳过比较后可能重复的像素内容当作已验证唯一帧。

Trace 容量从 2,048 增为 4,096，避免超过 35 FPS 时 60 秒采样溢出。容量和新增字段共增加约 272 KiB PSRAM 诊断存储；最终仍有约 6.98 MB 空闲 PSRAM。增加记录容量不改变显示画布分辨率。

### G. 文档、接口与一个编译警告

BSP 注释仍写着 native-endian，而实际传输边界已经是 CO5300 MSB-first；现已明确存储/线序与上层正常 RGB565 颜色值的区别。主机解码器直接按高、低字节组合，避免与编码器共享同一种错误而相互抵消。

修正 KK_UI 页面过渡中无符号除法结果再取负的 MSVC 警告，显式保持有符号运算；补齐两个 metrics getter 的 NULL 防护。当前最终 ESP-IDF、Windows 增量构建和 sanitizer 日志没有检出的 warning/error 记录；这不是所有平台所有构建模式的零警告保证。

## 7. 真实边界与下一步

本轮审计集中于最近修改的显示链：GL30 UI 调度、KK_UI、KK_OLED、BSP、主机呈现和 trace 工具，不是整个 STM32 电流环、硬件保护、机械装配或整机项目的完整放行审计。

最终测试没有真实 STM32 FAST/HAPTIC 流量，`motor_tx=0`。未验证实体触摸、实际面板颜色/撕裂的光学表现、真实编码器闭环输入、UART 满负载、电机运行或数小时热稳定性。122 幅同源画面一致证明的是绘图输出内容，不是实屏光学无撕裂。现有网页预览进程没有在本轮重启，不能假定其已加载新 DLL。

当前限制已经不再是菜单的整帧比较：最终 send wall P95 约 **26.9 ms**，绘制 P95 约 **21.5 ms**。**还没有证明 40 FPS，也没有证明所有应用都能达到 35.7 FPS。** 计时器等页面的完整 UI 调用仍可明显慢于菜单；它们本轮通过的是功能回归，性能应另设工作负载量测。

下一阶段应分别量测送屏条带/描述符提交开销与各应用光栅热点，而不是再次单纯压低刷新周期。当前保留 28 ms 配置和上述实测抖动统计，不将有限测试中的最大值当作长期上界保证；CPU、PSRAM 与 QSPI 时钟配置未在本轮改变，`sdkconfig` 与修改前逐字节相同。
